## 2. Paper trading ("invest fake money to check the result")

This is the biggest of the four asks — it needs a **database**, which
the project doesn't have yet (everything today is stateless: fetch from
Yahoo/News, compute, return). Designed but not built yet; here's the plan:

**Data store:** Supabase free tier (500MB Postgres, no cost). Clerk
stays as the identity provider — Supabase is used purely as a database,
keyed by Clerk's `userId`, no need for Supabase's own auth.

**Schema (sketch):**
```
paper_accounts   (user_id PK, cash_balance, created_at)
paper_positions  (user_id, ticker, quantity, avg_entry_price)
paper_trades     (id, user_id, ticker, side[BUY|SELL], quantity, price, executed_at)
```

**Flow:**
1. On first visit, a signed-in user gets a virtual account seeded with
   ₹1,00,000 (configurable).
2. On any stock page, an authenticated user gets a "Paper Trade" panel:
   Buy/Sell at the current live price, quantity input. This is a
   simulated fill only — no broker, no real money, clearly labeled.
   A "Trade at AI's suggested entry" quick-action can pre-fill from the
   swing setup's entry zone, directly tying the AI call to a testable
   outcome — this is probably the single best feature for building
   trust in the recommendations.
3. New **`/portfolio`** page: current positions with live unrealized
   P&L (current price vs. avg entry, pulled from the existing price
   API), realized P&L from closed trades, and a trade history table.
4. Backend: new FastAPI routes under `api/routes/portfolio.py` —
   `POST /api/portfolio/trade`, `GET /api/portfolio`, `GET
   /api/portfolio/history`. Needs Clerk JWT verification on the backend
   (currently the FastAPI backend has zero auth — every route is public
   market data with nothing to protect; this is the first feature that
   actually needs it).

**Why not build it today:** this is a real schema + a new backend auth
layer + several new frontend screens — rushing it in the last hour
before you're back risks shipping something broken. Better to do this
as a focused next session once you've confirmed the direction above.

## 3. Expanding to all Indian stocks

Currently: NIFTY 50 only (50 tickers), 8 of them pre-warmed/featured.
NSE has roughly **2,000+ listed equities**. Plan for getting there:

1. **Symbol list**: NSE publishes a full equity list (CSV via
   `nsepython`, already a project dependency, or NSE's own bhavcopy
   files). Swap the hardcoded `NIFTY_50` dict for a generated list —
   this part is cheap and mechanical.
2. **Search stays client-side fine** — even 2,000 items is small for a
   JS array filter, no architecture change needed there.
3. **Pre-warming can't cover everything** — the current background loop
   re-warms 8 stocks every 4 minutes; at 2,000 stocks that's not
   feasible on a free-tier single instance. Realistic approach: keep
   pre-warming a curated "popular/most-searched" set (maybe top 50–100
   by actual traffic once there's usage data), and let everything else
   compute on-demand with the existing cache (still fast on repeat
   views, just not instant on first view).
4. **Rate limits get more real** at this scale — see the yfinance
   section below, this is exactly where it starts to matter.
5. **Sequencing**: get the full symbol list in and searchable first
   (cheap, low risk), THEN decide on pre-warming scope once you can see
   real usage patterns — no point over-engineering caching for stocks
   nobody looks at.

I'd suggest doing this *after* deployment (from `NEXT_STEPS.md`), not
before — easier to make the pre-warming/caching calls with real traffic
data than to guess now.

## 4. Model accuracy — the HDFC-only problem (you were right to flag this)

Confirmed by reading the code: `lstm_model_path`, `tcn_model_path`, and
`ppo_model_path` are **hardcoded to the same HDFC Bank-trained model
files for every single ticker**, in both `app.py` and `api/compute.py`.
So today, asking about Reliance or TCS runs those tickers' price data
through a model that only ever learned patterns from HDFC Bank's
history. That's a real accuracy problem, not a minor one.

**The good news, also from reading the training code**
(`src/dl/train.py`): the training function is already parameterized by
ticker (`train_dl_models(ticker=...)`) — it was just only ever *run*
once, on HDFC Bank. And the features it trains on — RSI, EMA-spread,
MACD-difference, ATR% — are all already scale-normalized indicators,
**not raw price levels**. That matters: it means the existing setup
isn't as broken as "trained on HDFC's ₹1,700 price scale, nonsense for
a ₹11,700 stock" — it's closer to "trained on one stock's *behavioral
patterns*, applied generically."

**Recommendation: one pooled multi-stock model, not 50+ per-stock ones.**
Rather than training a separate model per ticker (expensive to maintain,
and doesn't scale to "all Indian stocks" at all — you can't hand-train
2,000 models), retrain once on a **pooled dataset**: run the same
feature pipeline across every NIFTY 50 stock (later, every NSE stock),
concatenate all the (features → future 5-day return) examples into one
big training set, and train a single LSTM/TCN on that. Because the
features are already scale-normalized, this is technically sound and is
standard practice — a model that's seen thousands of examples across
many stocks and sectors generalizes far better than one that's seen one
stock's history, and it scales to new tickers automatically (no
per-stock retraining needed as the universe grows).

**This is exactly what Colab is good for** — free GPU/TPU access for a
one-time (or periodic) training run. Concretely: loop
`train_dl_models`-style logic over all 50 (later, all NSE) tickers,
pool the datasets, train once, save as `lstm_general_v1.pt` /
`tcn_general_v1.pt`, download and drop into `models/`. The PPO agent
(`src/rl/train.py`) should get the same treatment — same idea applies.

**Sequencing suggestion:** do this retraining *before* the all-stocks
rollout, not after — no point expanding coverage on a model that's
giving everyone HDFC Bank's opinion.

## 5. yfinance — do we need to replace it?

**Short answer: not yet, but the resilience work already done today
buys real time, and it's worth planning the swap before real scale.**

What's true right now:
- `yfinance` is unauthenticated scraping of Yahoo Finance, not an
  official API. It's already been flaky twice this project (the
  original "no price data" bug, and a transient-failure-getting-cached
  bug found during today's audit) — both fixed with retries and
  smarter caching, but the underlying fragility doesn't go away.
- At NIFTY 50 scale with the existing 5-minute cache, this is fine.
- At "all Indian stocks + real user traffic" scale, more concurrent
  requests to Yahoo's undocumented endpoints raises real risk of
  IP-level rate limiting or blocking — which would take down price data
  for *everyone*, not just degrade gracefully.

**Free-tier alternatives, honestly assessed:**
| Option | Verdict |
|---|---|
| NSE India's own endpoints (via `nsepython`, already a dependency) | Same category of risk — unofficial scraping, NSE's site is if anything more aggressive about blocking bots |
| Alpha Vantage free tier | Only 25 requests/day — too limited to be useful here |
| Twelve Data free tier | ~800 requests/day, has NSE symbols — the most realistic free upgrade path if yfinance becomes unreliable |
| Kite Connect (Zerodha) | Real-time, reliable, built for this — but **paid** (~₹2,000/month), so out of scope per your "free only" instruction for now |

**Recommendation:** keep yfinance for now with the resilience already
built in (retries, negative-result-doesn't-cache, generous TTLs to
minimize request volume). Revisit only if you start seeing real
blocking/rate-limit errors in production, or once there's revenue to
justify a paid feed like Kite Connect. Don't spend effort replacing a
working thing pre-emptively — but keep this doc as the trigger for when
to revisit.
